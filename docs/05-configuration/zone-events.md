## Forcing/activating events (`ConfigureGlobalEvents{ forceEvents = {...} }`) — Q10

*(file, 2026-10-11)* An earlier review flagged every `forceEvents` block in the shipped
`cloud/data/default_platform_config.lua` as "commented out" (`ConfigureScriptsServer`,
around line 1008). Reading the comments there in full gives the field schema
and several worked examples (also commented) that the original operators used
to open/close world events by hand:

| Field | Type | Meaning (from the Russian comments) |
|-------|------|--------------------------------------|
| `eventDefName` | int | the event id (table above, older-numbering caveat applies) - if no instance of this event exists for the location it is **created**, otherwise the given fields are **modified in place** |
| `disableCreate` | bool | do not create a new instance; only modify one that already exists |
| `removeEvent` | bool | delete the event instance for that location |
| `eventLocation` | int | the open-world zone/location id the event applies to (a `SpaceZone` id) |
| `newEventState` | int | set the event's state/countdown; either a plain duration in seconds (`60*60*3` = 3 hours, as a literal expression) or one of the `ai.ScriptsServer` sentinel constants above (e.g. `TIMEOUT_EVENT` to force immediate expiry) |
| `eventParams` | table | event-specific parameter overrides (opaque per event def, left empty in every shipped example) |

`forceEvents` is a plain array of such records, passed once per
`ScriptsServer:ConfigureGlobalEvents({ forceEvents = { {...}, {...} } })`
call. The shipped file keeps four full example blocks (pre-event, "on start",
"on start with counter-attacks [not ready for November]", and an operator's
own debug variant) plus a short one-liner
(`forceEvents = { { eventDefName = 4, eventLocation = 247, newEventState = 998 } }`),
**all commented out** - a stock node runs with no forced events and whatever
state `ScriptsServer` computes on its own.

Two more controls in the same function: `ScriptsServer:SetTimerScale(n)`
(shipped as `1`, i.e. no scaling) and the commented
`ScriptsServer:OnSetTimerScale(60*60)` ("not all parameters support
acceleration") - a lever for speeding up event timers on a test node.

**To force/inspect an event on a node** (recipe, untested - runtime item):
uncomment and edit one `forceEvents` block (or add a new one) with the
*current* event id from the table above, the target zone id, and either a
duration or a sentinel `newEventState`; restart `ScriptsServer` (priority 0,
started last) and watch its log for `eventDefName`/`eventLocation` lines.
