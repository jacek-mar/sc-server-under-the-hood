## 5. Findings

1. **No exploit-mitigation linker flags** (ASLR/DEP/CFG) on 23 of the shipped game/service executables (linker 10.0, i.e. Visual C++ 2010 era); `mongod.exe` has ASLR+DEP. All executables carry an Authenticode security directory (certificate not validated here). *(file)* Hardening: the host can force ASLR/DEP via Windows Exploit Protection per executable (untested, may break the engine) - see [security.md](../07-administration/security.md) S-20.
2. **No executable imports OpenSSL's `libssl`** (24 of the executables, including the client and every service): only `libcurl.dll` links `libssl-1_1_tg.dll`. The services use `libcrypto` primitives directly - `RSA_*`/`PEM_read_bio_RSAPrivateKey` (all), `BN_*` incl. `BN_mod_exp` and `AES_cbc_encrypt`, `SHA1`/`SHA256` (Shard, DedicatedServer, client). No `SSL_CTX_new`/`TLSv1` strings exist in Shard, LoadBalancer, DedicatedServer or `game.exe`. So the client<->cloud transport is **not TLS** as far as static evidence goes (RakNet-style custom handshake with RSA key material and AES-CBC; static linking of a TLS library cannot be excluded without a capture, SV-9; the 2026-10-12 captures found no TLS). This contradicts the community assumption in Q24/S-19 that the password travels inside TLS.
3. **Hardware/host fingerprint APIs** in `DedicatedServer.exe`, `LoadBalancer.exe` and `game.exe`: `GetCurrentHwProfileA`, `GetComputerNameA`, `GetAdaptersInfo`, `GetUserNameA`, `EnumDisplayDevicesA` - consistent with the DB fields about unique PC fingerprints (`isSingleUidOnPC`). The client also enumerates running processes (see protocol-observed.md).
4. **`pdh.dll` in the Hub** = performance counters for the status page; `CreateProcessA` + `CreatePipe` = the Hub spawns and supervises the services.
5. `StatServer.exe` was last built 2013-11-08 (never rebuilt, consistent with not being started).
6. Reading aids: H = Shannon entropy of a section; ordinary code/data sits at 5.5-6.8, packed data would be > 7.2 (none found).
